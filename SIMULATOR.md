# Cyber Attack & Defense Simulator

A safe, non-destructive cyber-range module bolted onto the Cybersecurity
Digital Twin, at `/simulator`.

## Safety guarantee

Nothing in this module performs a real action against any system. There
is no malware, no exploit code, no payload, no credential theft, no
scanning, and no network traffic generated by a simulation. Every
"attack" is a deterministic graph traversal over a topology the user
builds in the browser, evaluated against a small set of transparent
rules (see `backend/app/simulation_engine/engine.py`). The only outputs
are: a per-node state label (`NORMAL`, `COMPROMISED`, `BLOCKED`, ...), a
0-100 "Project Risk Score," and a plain-language explanation built from
the topology's own declared field values.

## How the simulation engine works

See the module docstring in `backend/app/simulation_engine/engine.py`
for the full algorithm. In short: given a scenario, an entry point, and
a topology (nodes + edges the client submits in the request body — this
is *never* the real Digital Twin database), the engine does a bounded
breadth-first traversal from the entry point. At each hop it checks,
in order:

1. Is there a firewall (on the node, or a global "Enable firewall rule"
   defense) and is the scenario network/application/malware category?
   → path **blocked** here.
2. Is the scenario identity-category with an MFA prerequisite, and is
   MFA present (on the node, or globally)? → path **detected/blocked**
   here.
3. Is network segmentation present and are we past the first hop?
   → path **isolated** here.
4. Otherwise the node becomes **compromised** (or **detected**, if
   monitoring is present), and traversal continues from it.

This is the same rules-engine pattern described in Section 17 of the
module spec, implemented literally rather than described abstractly.

## Why the topology is client-submitted, not persisted

Section 27 of the spec is explicit: what-if branches must never modify
the real environment, only "the digital twin simulation." Rather than
build a second, parallel persistence layer for simulator topologies in
this pass, the simulator's canvas state lives in the browser (React
state + `localStorage` for saves) and the backend is a pure function:
topology in, outcome out. This keeps the safety property structurally
guaranteed — there is no code path in `simulation_engine/` that writes
to the `assets` table — at the cost of simulator topologies not yet
being shareable across devices or users. See "Suggested next steps"
below for the persistence path if that's wanted later.

## Suggested next steps

1. **Persistence:** add `simulator_workspaces` and `simulator_runs`
   tables (schema sketch already implied by `SimulationRunResponse`)
   so saves survive beyond one browser's `localStorage` and can be
   shared with a team.
2. **AI Copilot (Section 30):** once the Phase 7/8 LLM + RAG pipeline
   described in `ML_MODELS.md`'s parent project exists, the copilot's
   answers should be generated by feeding it the *actual* last
   `SimulationRunResponse` JSON as grounding context — never letting it
   invent events, per the module spec's explicit requirement.
3. **Defense Optimizer / Attack Path Predictor scale-up:** both
   currently re-run the full deterministic engine once per candidate
   (7 defenses, or `scenarios × attack-side nodes`). Fine at demo scale;
   for large topologies, cache engine runs or prune candidates first.
4. **Undo:** a simple command stack (push a topology snapshot before
   each mutating action) would satisfy Section 37's Ctrl/Cmd+Z shortcut
   without much new infrastructure.
